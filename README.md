# MVP AI-бот для малого бизнеса (шаблон под клиента)

Telegram-бот, который отвечает клиентам на частые вопросы на основе базы знаний
конкретного бизнеса (текст в `config/client_config.yaml`). Если бот не уверен в
ответе или вопрос выходит за рамки базы знаний — передаёт диалог владельцу.

Под нового клиента меняется **только** `config/client_config.yaml` — код трогать не нужно.

## Стек

- Python 3.11+
- [python-telegram-bot](https://docs.python-telegram-bot.org/) (async)
- LLM через OpenAI-совместимый API (OpenRouter, Inception и т.п.)
- Конфигурация: `.env` (секреты) + `config/client_config.yaml` (бизнес)

## Структура

```
project/
├── main.py                 # точка входа, запуск бота
├── config/
│   ├── client_config.yaml  # настройки конкретного клиента (менять под клиента)
│   └── settings.py         # загрузка .env и конфига, валидация
├── handlers/
│   ├── message_handler.py  # приём сообщений, вызов LLM, роутинг, fallback
│   └── owner_handler.py    # уведомление владельца бизнеса
├── services/
│   ├── llm_client.py       # обёртка над вызовом LLM (таймаут, ошибки)
│   └── fallback.py         # определение «передать человеку»
├── logs/                   # logs/bot.log — логи работы
├── .env.example            # шаблон переменных окружения
└── requirements.txt
```

## Как запустить локально

1. Установите зависимости (рекомендуется виртуальное окружение):
   ```bash
   python -m venv .venv
   .venv\Scripts\activate        # Windows (в Git Bash: source .venv/Scripts/activate)
   pip install -r requirements.txt
   ```
2. Создайте `.env` из шаблона и заполните:
   ```bash
   cp .env.example .env
   ```
   Нужны: `TELEGRAM_BOT_TOKEN` (от @BotFather), `LLM_API_URL`, `LLM_API_KEY`, `LLM_MODEL`.
3. Заполните `config/client_config.yaml` (см. ниже).
4. Запустите бота:
   ```bash
   python main.py
   ```

## Как настроить под нового клиента

Отредактируйте **только** `config/client_config.yaml` и перезапустите бота:

| Поле                     | Что это                                                           |
|--------------------------|-------------------------------------------------------------------|
| `business_name`          | Название бизнеса (в промпте и сообщениях о передаче)              |
| `tone`                   | Тон общения: «дружеский, на „ты"» / «формальный, на „вы"»         |
| `language`               | `ru`, `kk` или `auto` (автоопределение языка сообщения)           |
| `knowledge_base`         | База знаний: часы, цены, FAQ, «что нельзя обещать клиенту»        |
| `style_examples`         | 2-3 примера тёплого ответа (few-shot) — модели копируют стиль     |
| `owner_telegram_chat_id` | Куда пересылать нестандартные вопросы                             |
| `fallback_triggers`      | Ключевые слова, вызывающие немедленную передачу человеку          |
| `llm.*`                  | Модель, temperature, max_tokens, таймаут (сек)                    |

### Как узнать `owner_telegram_chat_id`

Напишите боту любое сообщение и откройте `logs/bot.log` — там появится
`user_id`; для личного чата он равен chat_id владельца. Впишите его в
`owner_telegram_chat_id` и перезапустите бота.

### Как узнать `owner_telegram_chat_id`

Напишите боту любое сообщение и откройте `logs/bot.log` — там появится
`user_id`; для личного чата он равен chat_id владельца. Впишите его в
`owner_telegram_chat_id` и перезапустите бота.

### Переменная `OWNER_CHAT_ID_OVERRIDE` (для тестов)

Если задать в `.env` переменную `OWNER_CHAT_ID_OVERRIDE=<chat_id>`, она
**перекрывает** `owner_telegram_chat_id` из `client_config.yaml`. Так можно
проверять уведомления с отдельного тестового аккаунта, не трогая конфиг
клиента. Оставьте значение пустым для продакшена — приоритет у yaml-конфига.

## Как это работает

1. Пользователь пишет сообщение боту.
2. Если в тексте есть слово из `fallback_triggers` — сразу fallback.
3. Иначе запрос к LLM: system prompt = роль + `tone` + `language` +
   `knowledge_base` + правило «отвечай только по базе; если не знаешь — начни
   ответ с `[HANDOFF]`».
4. Если в ответе модели есть токен `[HANDOFF]` — клиент получает вежливое
   «передаю вопрос…», а исходное сообщение и username/chat_id уходят владельцу.
5. Таймаут LLM (по умолчанию 15 сек) и ошибки API тоже трактуются как fallback:
   клиент получает «Секунду, уточняю у …», владелец — уведомление.
6. Память диалога: последние 8 сообщений каждого чата хранятся в памяти
   процесса и передаются модели — бот понимает «а за латте?» без повторения
   контекста. Ограничения: история теряется при перезапуске бота и сбрасывается
   командой `/start`; базы данных нет (осознанно для MVP).

## Логи

`logs/bot.log` (ротация 1 МБ × 3 файла). На каждое сообщение: время,
user_id/username, текст входящего сообщения, был ли fallback и почему, время
ответа LLM. Полный текст ответов LLM не логируется — только факт успех/ошибка.

## Деплой на Railway / Render

В сервисе задайте переменные окружения из `.env.example`
(`TELEGRAM_BOT_TOKEN`, `LLM_API_URL`, `LLM_API_KEY`, `LLM_MODEL`) и укажите:

- **Railway**: команда старта `python main.py` (зависимости ставятся из `requirements.txt`).
- **Render**: Build `pip install -r requirements.txt`, Start `python main.py`.

Webhook не нужен — бот работает через long polling, порт не требуется.

## Что НЕ входит в MVP

База данных, векторный поиск, мультитенантность, напоминания, аналитика,
веб-админка — сознательно не реализованы (см. ТЗ п.9).
